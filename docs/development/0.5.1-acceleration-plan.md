# ZADU 0.5.1 acceleration plan

> Status: temporary working document. Keep this file until the 0.5.1 work is
> complete, then either promote it to maintained architecture documentation or
> remove it as part of the release cleanup.

## Objective

Make exact ZADU evaluation substantially faster and more memory-aware without
changing metric definitions or forcing users to install a hardware framework.
The existing NumPy API and exact CPU behavior remain the compatibility baseline.

Approximate algorithms are intentionally out of scope for 0.5.1. In particular,
this plan does not include approximate nearest-neighbor search, landmarks,
pair sampling, random-feature density estimates, or early stopping.

## Constraints

- Preserve public metric IDs, parameters, return keys, local-score shapes, and
  specification order.
- Keep the default installation usable without MLX or PyTorch.
- Keep the default execution path exact and deterministic wherever it already is.
- Never choose a lower precision or a different device silently.
- Treat numerical precision separately from algorithmic approximation. A user
  requesting `float32` may see normal floating-point drift, but every requested
  pair, neighbor, and iteration must still be evaluated.
- Preserve validation and defined failure modes for degenerate inputs.
- Measure warm execution, cold startup, transfer time, peak memory, and numerical
  delta separately so a fast device kernel does not hide setup costs.

## Baseline observations

Local profiling on an Apple M4 identified three different bottleneck classes:

1. Full ranking is dominated by dense distance matrices, full row sorts, and
   inverse rankings. At 5,000 samples, one dense float64 matrix is about 191 MiB
   and one int64 ranking matrix is another 191 MiB; sort temporaries drive peak
   memory much higher.
2. Several metric implementations add Python loops after those resources have
   already been computed. Representative NumPy prototypes showed large isolated
   speedups: about 29x for T&C, 6.5x for MRRE, 7.8x for LCMC, 17x for
   Neighborhood Hit, 130x for Topographic Product, and 2.5x for Procrustes.
3. Steadiness & Cohesiveness spends most of its measured CPU time in repeated
   cluster-pair distance calls rather than clustering itself. It needs a separate
   sparse and batched redesign.

Warm, device-resident experiments also showed that accelerators are resource
dependent: MLX and MPS can accelerate dense pairwise/ranking work, while exact
top-k FAISS on CPU can remain faster and far more memory-efficient. ZADU should
therefore plan resources independently instead of selecting one backend for an
entire run.

## Target execution model

The long-term exact execution path is:

```text
metric specifications
        -> exact resource requests
        -> planner (device, dtype, memory budget, reuse, lifetime)
        -> resource providers (NumPy/SciPy, FAISS, MLX, PyTorch)
        -> fused metric kernels
        -> scores plus separate run metadata
```

Resource contracts should describe what a metric needs rather than how to
compute it:

- `KNN(space, k)` for exact neighbor indices.
- `Rank(space)` or an exact rank-query resource for full rankings.
- `PairBlocks(space)` for streamed dense distances.
- `CondensedPairs(space)` for unique off-diagonal distances.
- `Density(space, sigma)` for shared density calculations.
- `SNN(space, k)` for sparse shared-neighbor graphs.
- `Triangles(embedding)` for Gap Index geometry.

The planner may mix providers in one run. For example, FAISS can provide exact
top-k neighbors while MLX provides a dense distance/rank resource. Resource
lifetimes must be explicit so original-space data can be reused and embedded-
space temporaries can be freed immediately after their last consumer.

## Public surface introduced with PR 2

The initial configuration exposes only capabilities implemented by the exact
NumPy/FAISS CPU path:

```python
from zadu import ExecutionConfig, ZADU

execution = ExecutionConfig(
    backend="auto",       # or numpy
    device="auto",        # or cpu
    memory_budget="4GiB",
)

runner = ZADU(specs, orig, execution=execution)
scores = runner.measure(emb)
```

All 0.5.1 execution is exact, so the configuration exposes no approximation
mode. Existing constructor calls remain valid and use the NumPy/FAISS exact path.
Backend-specific device and precision options will be added only alongside the
providers that can honor them.

Execution diagnostics belong in `runner.last_run_info` (and eventually an
optional `return_info=True` result), not inside metric score dictionaries. The
metadata should record selected providers, device, dtype, resource timings,
transfer/compile timings where relevant, peak-memory estimates, and cache reuse.

## Work packages and PR order

### PR 1 — exact NumPy kernel vectorization ✅

- Add small chunked row-wise primitives with a roughly 64 MiB temporary budget.
- Vectorize T&C, class-aware T&C, MRRE, LCMC, and Neighborhood Hit.
- Replace the cubic Topographic Product loop with gathered distance ratios and
  cumulative logs while preserving its mathematical definition and errors.
- Batch centered cross-covariance and SVD work for local Procrustes.
- Add independent slow reference oracles and an isolated benchmark script.
- Do not change public APIs, scheduling, backends, or packaging.

Acceptance targets on representative inputs:

| Kernel | Minimum target |
| --- | ---: |
| T&C / class-aware T&C | 10x |
| MRRE | 4x |
| LCMC | 5x |
| Neighborhood Hit | 10x |
| Topographic Product | 50x |
| Procrustes | 1.5x |

Small inputs should regress by less than 10%. Shared CI should test correctness,
not hard-code wall-clock thresholds; benchmark history can be added later on a
stable runner.

### PR 2 — exact resource contracts and planner foundation ✅

- Introduce `engine/config.py`, `engine/resources.py`, `engine/planner.py`, and a
  narrow internal backend protocol.
- Translate registry cache flags into typed resource requests.
- Preserve the current scheduler as the initial NumPy provider.
- Track construction time, consumers, reuse, and last-use lifetime per resource.
- Add `last_run_info` without changing score results.
- Test mixed `k`, mixed resource providers, ties, duplicate points, and planner
  determinism.

### PR 3-A — fused exact pair statistics ✅

- Add dense-reuse, condensed upper-triangle, and block-streaming strategies for
  exact unique point pairs.
- Fuse Stress, Scale-Normalized Stress, and Pearson into one stable sufficient-
  statistics pass.
- Select bounded block sizes from `memory_budget`, report planned peak working
  memory, and release per-run pair resources after their final consumer.
- Preserve the dense scheduler when mixed neighborhood/ranking requirements need
  its legacy tie behavior.
- Add dense-reference parity tests and isolated cold/warm time and RSS
  benchmarks.

Local Apple M4 validation at `n=2,000`, 20 original dimensions, and three fused
metrics measured 3.91x cold / 5.84x warm speedup with condensed storage and
reduced process peak RSS from about 402 MiB to 199 MiB. A 16 MiB streaming plan
measured about 5.29x cold and warm speedup with about 136 MiB process peak RSS;
the maximum score delta was `1.67e-16`. These are recorded review measurements,
not shared-CI timing gates.

### PR 3-B1 — shared exact ordered-pair resources ✅

- Replace the persistent dense matrices used by Spearman and Non-Metric Stress
  with compact embedded-space condensed distances.
- Cache one original-space pair order and tie-aware ranks across repeated
  embeddings, and fuse both ordered metric results into one per-run resource.
- Preserve the existing direct metric APIs, exact duplicate/tie behavior, dense
  reuse for mixed resource plans, and degenerate-input errors.
- Reject explicit budgets that cannot hold the exact ordering plan before any
  distance allocation begins.

Local Apple M4 validation at `n=2,000`, 20 original dimensions, and both ordered
metrics measured 1.07x cold / 1.59x warm speedup, reduced process peak RSS from
about 480 MiB to 369 MiB, and reduced planned cache from 64.0 MB to 48.0 MB. The
maximum score delta was `2.85e-15`.

### PR 3-B2 — exact Topographic Product selected distances ✅

- Replace persistent dense distance matrices with exact stable-kNN tables built
  from bounded distance-row blocks.
- Evaluate only the four `O(nk)` selected-distance tables needed by the metric,
  reduce them immediately, and keep no selected-distance table in the cache.
- Compute the largest requested `k` once and expose exact prefix results for all
  smaller Topographic Product specifications.
- Preserve dense tie order, geodesic behavior, duplicate-point errors, original
  neighbor reuse, and explicit preallocation guards.

Local Apple M4 validation at `n=2,000`, 20 original dimensions, and `k=20`
measured 1.75x cold / 1.78x warm speedup, reduced process peak RSS from about
311 MiB to 176 MiB, and reduced persistent cache from about 64.6 MB to 0.64 MB.
The score was bit-identical to the dense reference.

### PR 3-B3 — remaining memory-bounded CPU resources and kernel fusion

- Use `int32` indices/ranks when the sample count safely fits, with an `int64`
  fallback.
- Fuse exact consumers:
  - DTM and KL divergence from one density resource per `(space, sigma)`.
  - T&C, class-aware T&C, and MRRE from shared gathered ranks.
  - LCMC, Neighborhood Hit, and Neighbor Dissimilarity from shared neighbors.
  - Spearman and non-metric stress from shared exact condensed/order resources.
- Enforce `memory_budget` before allocation and free resources after last use.

### PR 4 — Steadiness & Cohesiveness exact CPU acceleration

- Skip Euclidean distance construction when validated kNN resources are supplied.
- Keep SNN graphs sparse and remove dense `.toarray()` paths.
- Batch cluster-pair similarity/distance calculations instead of calling a scalar
  helper tens of thousands of times.
- Generate deterministic per-iteration seeds first, then parallelize independent
  iterations with bounded worker memory.
- Maintain the existing `snc==0.2.0` compatibility oracle and add fixed-seed
  single-worker versus multi-worker parity tests.

### PR 5 — repeated-embedding and multi-k execution

- Add `measure_many(embeddings, labels=None)` after planner/resource metadata has
  stabilized.
- Reuse immutable original-space distances, ranks, densities, and neighbors.
- Batch embedded-space work when a provider benefits from it while preserving
  input/result order.
- Compute the largest requested exact `k` once and expose prefix views to smaller
  `k` consumers.
- Document thread/process safety and bound parallel memory by the execution
  configuration.

### PR 6 — MLX exact backend preview

- Add an optional, lazily imported MLX provider for pairwise distance, full
  ranking/inverse ranking, exact top-k, reductions, and supported batched linear
  algebra.
- Account separately for compile, transfer, and warm execution time.
- Use unified-memory-aware buffer reuse on Apple Silicon.
- Require explicit `float32` when the selected MLX GPU cannot honor `float64`;
  never downgrade precision automatically.
- Fall back per resource, not per run, when an exact MLX primitive is unavailable.

### PR 7 — PyTorch exact backend preview

- Add an optional, lazily imported PyTorch provider for CPU, CUDA, and MPS.
- Implement exact `cdist`, stable row ranking, exact `topk`, reductions, and
  batched SVD where parity requirements are met.
- Reuse device-resident resources within a run and synchronize only at timing or
  result boundaries.
- Detect unsupported operations and fall back per resource with the choice
  recorded in run metadata.

### PR 8 — packaging, CI, documentation, and 0.5.1 release gate

- Keep the base wheel pure Python and keep backend imports lazy.
- Offer focused extras rather than an `all` extra, for example `zadu[torch]` and
  platform-specific MLX extras where dependency markers can express support.
- Detect externally installed FAISS GPU builds; do not promise an unsupported
  official pip distribution through a ZADU extra.
- Reserve a `zadu.backends` entry-point group so third parties can package a
  backend without entering ZADU's core dependency set.
- Add backend parity jobs, dtype-specific tolerances, duplicate/tie datasets,
  memory-budget tests, and scheduled benchmark jobs.
- Publish a backend capability table and explain cold versus warm measurements.

## Internal package shape

The exact file split may evolve, but dependencies should point inward through a
small protocol:

```text
src/zadu/
  engine/
    config.py
    planner.py
    resources.py
    result.py
  backends/
    base.py
    numpy_backend.py
    faiss_backend.py
    mlx_backend.py
    torch_backend.py
  kernels/
    neighborhood.py
    pairwise.py
    density.py
    snc.py
```

Avoid adopting a full generic array API internally. Stable sort behavior, sparse
graphs, SVD, device synchronization, and memory ownership differ enough between
providers that a narrow ZADU resource protocol is easier to test and maintain.

## Benchmark and release gates

Every benchmark record should include metric/resource name, `n`, input dimension,
`k`, dtype, provider/device, cold and warm time, transfer/compile time, peak RSS or
device memory where available, speedup against the NumPy baseline, numerical
delta, and system metadata.

The 0.5.1 release candidate should satisfy all of the following:

- At least 3x faster for a representative multi-metric exact specification.
- PR 1 kernel targets remain met on the maintained benchmark machine.
- A warm accelerator full-ranking path is at least 8x faster on its documented
  target workload, including a separately reported cold measurement.
- The configured memory budget is honored or the run fails before the oversized
  allocation with an actionable message.
- NumPy exact results pass legacy and new reference-oracle tests.
- MLX and PyTorch results pass dtype-specific parity tests on supported runners.
- Base-install tests prove neither optional framework is imported or required.

## Explicit non-goals

- No approximate algorithms or approximate execution mode.
- No silent precision downgrade, device migration, or metric substitution.
- No monolithic backend selection that forces every resource onto one device.
- No hard wall-clock pass/fail threshold on noisy shared pull-request runners.
- No ZADUVis performance redesign in 0.5.1.
